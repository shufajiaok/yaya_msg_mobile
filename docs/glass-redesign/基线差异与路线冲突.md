# 基线差异与路线冲突（P0 动工前拦截）

> 2026-11-07 · 动工前核查发现。**结论：P0 代码改动暂停，等用户拍板路线后再动。**
> 依据用户既定规矩：大改前先列清单；AI 改动超出指定范围立即纠正撤回；最小成本。

## TL;DR

方案 v2.1 全部基于 `e324df4`（v2.7.5 / Expo 54），但工作副本 `c428b29`（Expo 55）**已经存在一套完整的玻璃实现**，且技术路线不同。若照 v2.1 P0 直接新建 `src/theme/glass.ts`，会造出**第二套参数来源**，违反项目现有代码里「玻璃的唯一出口是 GlassSurface」的约定。

## 2. 根因

1. 调研快照锁定在 2026-09-11 的目标 commit，之后 fork 用 `merge-upstream` 同步到了源仓库最新 main。
2. 朋友仓库在 `e324df4` 之后自行完成了 Expo 55 升级与玻璃组件落地，但方案文档未同步这部分事实。
3. 我此前建议「以最新 main 为基线」时，只核对了依赖版本，**未先复核 main 的玻璃实现现状**，导致清单与实况脱节。

## 3. 冲突点：为什么不能直接按 P0 清单动工

| v2.1 P0 项 | 现状冲突 | 直接执行的后果 |
| --- | --- | --- |
| 新建 `glass.ts` 作「玻璃参数单一来源」 | 已有 `GlassSurface` 自称唯一出口，且有自己的 `MATERIAL` 表 | 两个「单一来源」，参数分裂 |
| zustand 四倍率全局调参 | 现有组件按 `role/intensity` 静态分档，无全局可变状态 | 滑块改了四倍率但组件不订阅＝无效改动 |
| `canBlur(≥31)/canLens(≥33)` 双档 + `degrade()` 六类 | 已有 `useGlassSupport()` 的 `tier` 分级与兜底 | 两套降级链，行为不确定 |
| `GlassSurface` 单一容器（M23） | 已有同名组件 338 行，职责相同 | 组件重名 / 重复实现 |
| P1 改造 `AppTabBar` / `ScreenHeader` | 这些页面可能已接入新玻璃组件 | 改到一半发现已是目标形态，返工 |

## 4. 两条路线

### 路线 A · 适配现有实现（推荐）

以 `c428b29` 为基线，**不新建第二套参数源**。把 v2.1 的**规范约束**作为验收标准，落到已有组件上：

- `glass.ts` 若仍要建，定位改为「**把 `GlassSurface` 的 `MATERIAL` 表、`role` 档位、`intensity` 默认值收拢成单一 token 文件**」，由 `GlassSurface` 引用，保留其对外 API。
- 四倍率调参改为**在现有 `role/intensity` 体系上叠加**（例如全局 `intensityScale`），或直接沿用 `useGlassSupport()` 的 `tier` 做降级，不引入平行状态机。
- 仍需做且无冲突的部分：**`colors.ts` 补 4 套色 token**、**字号 ≥11sp 断言**、**同心圆角公式**、**a11y 降级矩阵**、**CI 静态守卫**、**设计文档收敛**。
- 需先做一次「现有 6 个玻璃组件 vs Apple 规范」的增量盘点，产出**修订版 P0 清单**再动代码。

**优点**：不推翻朋友已完成的 819 行实现；不丢 PiP 修复与 Expo 55；改动面最小。
**成本**：方案 v2.1 的 P0 清单需重写一轮（约 1 次盘点）。

### 路线 B · 回退到 `e324df4` 严格按原方案

从 `e324df4` 建分支，按 v2.1 P0 从零实现路径 A+。

**优点**：与 5 份方案文档 100% 对齐，行号/清单全部有效。
**成本**：丢掉后续 PiP 修复、Expo 55 升级、已有玻璃组件；浅克隆需单独 fetch 该 commit（代理不稳，可能失败）；相当于在旧版本上重做一遍别人已做的工作。
